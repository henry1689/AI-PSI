# ADR-0018：反馈、经验与改进提案（阶段 6）

- **状态**：已接受
- **日期**：2026-09-18
- **相关**：ADR-0002（事件与状态）、ADR-0004（记忆策略）、ADR-0005（策略不得自动生效）、
  ADR-0012（范围边界）、ADR-0015（阶段 3 实现决策）、ADR-0017（长期记忆）

## 背景

阶段 6 的交付是"反馈、经验与改进提案"（任务书 §11、§12.2、§12.4）。
验收条件是三条：

1. 单次普通经验不能推广；
2. 三次同类错误可生成 Proposal；
3. Proposal 始终需要外部审批。

这三条都是**否定式**的——它们说的是"什么不会自动发生"。
本 ADR 记录我们如何让这三件事在代码里**做不到**，而不是靠约定不做。

---

## 1. 学习链路不接收自由文本

`RoundRecord` 与 `ErrorSignals`（`learning/error_classifier.py`、
`learning/experience_builder.py`）的字段集合里**没有任何一栏能装下
用户消息、模型输出或反馈正文**。反馈以**类型**参与（"用户纠正了"），
不以**内容**参与。原文留在事件流里，那是审计的地方。

两条理由，第二条比第一条重要：

1. 归因不该依赖对文本的语义理解——那是模型的工作，而模型的判断
   不该被直接固化成"系统学到了什么"；
2. 这些文本可能含用户隐私。把它们拉进学习链路，等于给隐私开了一条
   **谁也没打算开**的路。没有人会在评审时说"我同意把用户原话送给
   学习模块"，但一个 `user_message: str` 字段加进去时，没有人会反对。

因此这条边界不是写在文档里的，而是**钉在测试里**的：
`TestNoFreeTextEntersTheLearningChain` 断言两个 dataclass 的字段集合
逐字相等。加字段的人会看着它失败——而那一秒正是这个测试的全部意义。

## 2. 归因只做确定性判断，判不了就说不出来

`ErrorClassifier` 的每条判据都必须**可以被指出来**：回合在哪个阶段失败
（阶段映射是确定的）、元认知检出了什么、用户是否明确纠正过。
凡是需要理解语义才能判定的，一律不判——返回"无法归因"而不是一个
看起来合理的分类。

判据按**具体性**排序，先命中的胜出：

| 顺序 | 判据 | 类别 | 置信度 |
|---|---|---|---|
| 1 | 阶段映射已给出类别 | 直接采用 | MODERATE |
| 2 | 预算耗尽 | `PROCESS_ERROR` | MODERATE |
| 3 | 记忆写入被策略拒绝 | `MEMORY_ERROR` | MODERATE |
| 4 | 元认知检出范围漂移 | `SCOPE_ERROR` | MODERATE |
| 5 | 元认知检出无依据的确定性 | `CALIBRATION_ERROR` | MODERATE |
| 6 | `NORMATIVE` + `ANSWER` 自相矛盾 | `VALUE_SUBSTITUTION` | MODERATE |
| 7 | 反例被忽略 / 偏差风险偏高 | `REASONING_ERROR` | MODERATE / LOW |
| 8 | 用户明确否定反馈 | `UNKNOWN_ERROR` | LOW |
| — | 都不命中 | `None`（**不归因**） | VERY_LOW |

### 三个不显然的排序决定

**第 2 条排在第 8 条前面。** 用户纠正说明"有错"，元认知信号说明"错在哪"。
两者同时出现时，后者给出的类别比 `UNKNOWN_ERROR` 有用得多。
反过来排序会让所有"用户纠正过"的回合都归成同一个笼统类别，
模式发现因此失去分辨力。

**第 6 条（价值替换）的判据是结构性的，不看措辞。** 判断自己声明了
`NORMATIVE`（事实无法决定的价值选择），却给出了 `ANSWER`（可以给出结论）
——这两件事放在一起就是自相矛盾。而 `NORMATIVE` + `OUT_OF_SCOPE`
**不是错误**：诚实地说"这不是认知系统该回答的"正是任务书 §9.10
要求的行为。把它归成错误，等于教系统去回答它本该拒绝回答的问题。

**第 8 条给不出具体类别，而且理由里要说清为什么。** 用户反馈证明判断有误，
但错误类别需要理解用户在纠正什么——那是语义判断，确定性规则做不了。
给一个看起来具体的类别（比如一律判成 `FACTUAL_ERROR`）会让模式发现
把一堆互不相干的错误聚成一类，然后生成一个针对错误问题的提案。

### 阶段映射只有一份

`STAGE_ERROR_CATEGORY` 住在 `learning/error_classifier.py`，
`application/cognitive_runtime.py` 的 `_category_for` 导入它。
阶段 3 曾有一份副本，阶段 6 合并。

测试从**运行时的源码里读出**阶段名（`stage = "..."` 的正则扫描），
而不是抄一份清单——抄的清单在新增阶段时不会变，它会继续通过，
而新阶段在运行期悄悄得到 `UNKNOWN_ERROR`。

## 3. 🔴 未评估 ≠ 不成立

任务书 §11.3 给出五条**任一即可**的触发条件：

1. 同类错误至少出现 3 次；
2. 一个严重错误存在明确修复方向；
3. 离线评测暴露稳定退化；
4. 用户纠正显示现有规则具有系统性问题；
5. 相同认知模块连续低于阈值。

`PromotionEvidence` 对第 3、5 条使用 `bool | None` 与 `int | None`，
其中 **`None` 表示"未评估/未观测"，与 `False`/`0` 不是一回事**。

理由在后果上：把无法评估的条件当作"不成立"，会让系统**永远只从最容易
计数的那个条件（第 1 条）产生提案**——而"离线评测暴露稳定退化"恰恰是
最有价值、也最不可能被计数捕捉的那一类。

同样的原则出现在两个下游：

* `OfflineEvaluator.regressed()` 在没有对照数据时**抛错**而不是返回 `False`。
  返回 `False` 会让调用方把"没查"当成"查了没问题"；
* `UNAVAILABLE_METRICS` 是一份**清单**而不是注释。它出现在每一次评估
  结果里，让读报告的人一眼看到"哪些没算"，而不是从"报告里没有这一项"
  去推断——那正是最容易被忽略的一类遗漏。

`PromotionDecision.reasons` 里**包含未命中的条件为什么没命中**。
一份只有"为什么可以"的裁决，日后被质疑时回答不了"那另外四条呢"。

## 4. 🔴 反馈不得绕过写入策略

`POST /cognitive-rounds/{round_id}/feedback` 的 `allow_memory_update`
**不是"允许直接写记忆"**，而是"允许把这次反馈**提给**记忆写入流程"。
真正的写入仍然走 `MemoryWriteProposal → WritePolicy → MemoryService`
（ADR-0004）。把这条路径短路掉——比如在反馈服务里直接构造 `Memory`
落库——会让反馈变成一条绕过全部记忆红线的旁路，而它看起来只是
一次用户操作。

两条测试把这件事钉死：

* 注入一条**一律拒绝**的策略，确认反馈什么也没写；
* 用一段命中内容红线（§10.3）的正文——并且特意走**用户亲手写下的
  纠正**这个看起来最正当的入口——确认它同样被挡住。

### 只有 CORRECTION 与 CLARIFICATION 能带出记忆

这两类是**唯一**提供了新信息的反馈："我说的其实是 X"。
`AGREEMENT` / `ACKNOWLEDGEMENT` / `RATING` 不含关于世界或用户的新事实；
`DISAGREEMENT` 只说"你错了"，没说对的应该是什么。拿它们写记忆，
等于把噪声记成事实——而记忆一旦写错，它会在之后**每一轮**里持续影响判断。

白名单是**白名单**：新增反馈类型时默认不允许带出记忆，
一个没想到过的新类型应该先被讨论，而不是先获得写记忆的能力。

### 反馈正文存进事件流

正文**必须**存下来。这与记忆审计负载的脱敏规则（§10.5）**不冲突**：
那条规则管的是"不得保留**被删除内容**的正文"，
而反馈正文是**对话记录**——事件流里本来就存着 `user.message.received`
的正文。摘掉它，这条事件就只剩"用户点过一次纠正"，
事后既说不清他纠正了什么，也说不清那条记忆是从哪句话来的。

### 🔴 事务顺序：反馈事件先落，记忆更新后做

两步**不在同一个事务里**，这是刻意的。反方向（记忆先写、事件后记）
的失败后果是"改了却没有记录"（ADR-0015 §5）——但在这里，
另一个方向的失败更严重：**用户说过的话丢失了**。

记忆没更新上，用户再说一次即可；反馈正文没记下来，它就真的没了。

两步通过共同的 `correlation_id` 关联，而记忆提案的
`source_event_ids` **直接指向那条反馈事件**，因此"这条记忆为什么会出现"
仍然可以追回来。`TestTheFeedbackRecordSurvivesAMemoryFailure`
用一条会在记忆写入时崩溃的服务实例把这条顺序钉死。

### 事件不预测结果

`user.feedback.received` 的负载里记录的是**这次请求是什么**、
以及**是否够格提给写入流程**；它**不记录** `memory_effect`。
把猜出来的结果写进不可变更的事件里，就是在制造一条会过期的记录——
真实结果是记忆层自己的事件（`memory.approved` / `memory.rejected`）说的。

同理，"没请求更新"（`MemoryEffect.NONE`）与"请求了但不满足"
（`NOT_ELIGIBLE`）是两种结果，不合并。

## 5. 提案状态机：一切都在"不能自动生效"这一侧

```
DRAFT → PENDING_EVALUATION → EVALUATED
                            ├→ REJECTED
                            └→ APPROVED_FOR_MANUAL_TRIAL
```

### 驳回与批准都必须先评估

`REJECTED` 与 `APPROVED_FOR_MANUAL_TRIAL` 的 `allowed_from` 都只有
`{EVALUATED}`。在 `DRAFT` 上调这两个接口得到 409 并附说明：

* 未经评估的批准 = 凭印象拍板；
* 未经评估的驳回 = 把"不想做"记成"做不了"，下一个人再遇到同类问题
  时只会看到"这条被拒了"，然后重新走一遍同样的路。驳回的成本本该
  换来一条经验。

`reason` 必填，同样是这个理由。

### `PENDING_EVALUATION` 在 V0.1 是一次原子穿越

它表示"已登记待评估、结论还没出来"。V0.1 没有后台评测器
（那是阶段 7 的 Eval Runner），因此不存在那个等待窗口——
登记的下一秒结论就到了。这个状态保留在类型与数据库里，
是为了阶段 7 接上评测器时**不需要改状态机**，
而不是因为它在 V0.1 里能被观察到。

> ⚠️ 这是本 ADR 里**最可能在阶段 7 被重新讨论**的一条。
> 到那时需要回答的是：谁把提案推进 `PENDING_EVALUATION`，
> 以及一条卡在评估中的提案多久算超时。

### 乐观锁是正确性要求，不是性能优化

两个评审同时对同一条提案点"批准"和"驳回"时，静默覆盖的结果是一条
提案**同时**被批准和驳回，而事件流里两条理由都在。

`ProposalService` 的每次流转都走 `save(bumped, expected_version=...)`，
版本不匹配抛 `OptimisticLockError`（API 上是 409）。
测试模拟"读到之后、写回之前，第一条流转已经提交"的第二个写入者，
断言它失败、状态不变、**且事件流里没有它的记录**。

> ⚠️ 那条用例是**顺序**执行的。它验证的是"带着过期版本号的写入会被拒"，
> 而不是真的并发调度——后者依赖事件循环的时机，写成断言会变成
> 一条时灵时不灵的测试。真正的并发语义由 PostgreSQL 实现承担，
> 并由契约测试 `test_stale_version_raises_instead_of_overwriting` 覆盖。

### 评估必须有口径

`ProposalEvaluation.evidence` **不得为空**，服务层抛 `ValueError`、
API 上是 422。理由是这条链路的核心承诺："结论：改善"而没有说
跟什么比、比了多少个样本，是一条**无法被复核、因而也无法被推翻**的记录——
而不可推翻的结论会永久影响策略。

`EvaluationVerdict` 含 `INCONCLUSIVE`。没有它，评估者只能在"有效"与
"无效"之间二选一，而"样本太少，看不出差别"是最常见、也最诚实的结果。
逼它变成其中一个，等于把噪声变成结论。

## 6. 新增两个事件类型（任务书 §5.2 清单缺失）

§12.4 要求 `approve-for-manual-trial` 与 `reject` 两个接口，
§5.2 的事件清单却只给了 `improvement_proposal.created` 与 `.evaluated`。

缺了它们，**人类做出的那个批准决定本身不会留下任何痕迹**——
而整条受控迭代链路存在的理由，正是这个决定要可追溯（不变量 11）。

因此新增：

* `improvement_proposal.approved_for_manual_trial`
* `improvement_proposal.rejected`

事件总数 34 → 36。这是 §5.2 清单的第四处补齐
（前三处：`cognitive_round.cancelled` / ADR-0012、
`cognition.analysis.completed` / ADR-0015、`memory.exported` / ADR-0017）。
`tests/unit/test_enums.py` 的条数钉死测试随之更新。

## 7. 经验不建表，提案建表

| | 存储 | 理由 |
|---|---|---|
| `Experience` | **留在事件流** | 不可变的观察，从不更新。建表只会引入"投影与事件流不一致" |
| `ImprovementProposal` | **建表** | 状态可变 → 需要乐观锁、按 id 取、按状态列表查询（同 `cognitive_rounds`，ADR-0002） |

这个对比是刻意的：判据是"**这个对象会被改写吗**"，不是"它重要吗"。

## 8. 不变量被削弱时进程不该起来

`reliability/invariants.py` 提供不变量的**运行期自检**，
`/health/cognitive` 把它作为 `invariants` 维度暴露。

宪法里写着"`ProposalStatus` 没有 ACTIVE 成员"，而当某天有人往枚举里
加了一个成员，宪法文档不会自己变——它依然写着那句话，依然通过所有
断言元组数量的测试。只有一条运行期检查能发现结构性的保证被削弱了。

三件事被检查（I01 / I10 / I11），而**检查方式是"试着构造"**：
构造 `ProposalStatus("active")` 会失败，这个失败**本身就是**
"类型里没有这个值"的直接证据——比读一遍成员列表更硬。

`TestTheCheckCanActuallyFail` 逐条把结构性保证按坏（把门槛改成 1、
把 `draft` 加进禁止值、把兜底断言改成空操作），要求自检把它们指出来。
**一组恒为绿的检查与没有检查是同一件事。**

未覆盖的不变量**不假装通过**：`HealthReport.unchecked_invariants`
显式列出它们，而 API 响应里的 `unchecked_invariants` 维度对用户可见。

数据库那一侧同样如此：`improvement_proposals.status` 的 CHECK 由
`ProposalStatus` 生成，实测 `INSERT ... status='active'`
被 PostgreSQL 拒绝（`ck_improvement_proposals_status_valid`）。

## 10. 本阶段明确不做的事

* **不自动生成提案**：`learning/` 的四个组件都是**纯函数**，
  没有任何定时器或钩子调用它们。提案的生成必须由一个显式的动作触发。
  这条边界在阶段 6 是刻意的——在阶段 7 有评测数据之前，
  自动生成提案意味着用噪声喂评审；
* **不做提案的影响面分析**：`possible_regressions` 是一段**模板文字**，
  不是计算出来的。真正的退化预测需要 Golden Dataset；
* **不自动执行被批准的提案**：`APPROVED_FOR_MANUAL_TRIAL` 之后
  发生什么由人决定（不变量 11）；
* **不做 `proposal_false_promotion_rate`**：它要跨版本跟踪提案的
  最终去向，属于长期运行指标；
* **`GET /users/{user_id}/beliefs`** 仍然不做（ADR-0017 §7）。
