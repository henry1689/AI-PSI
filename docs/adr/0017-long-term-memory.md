# ADR-0017：长期记忆（阶段 5）

- **状态**：已接受
- **日期**：2026-09-18
- **相关**：ADR-0002（事件与状态）、ADR-0004（记忆策略）、ADR-0009（内存适配器）、
  ADR-0012（范围边界）、ADR-0015（阶段 3 实现决策）、ADR-0016（真实 LLM Provider）

## 背景

阶段 5 的交付是"长期记忆"：Memory Repository、pgvector 检索、冲突/过期/取代、
用户纠正、删除与导出、用户隔离测试（任务书 §18）。

阶段 3 已经交付了其中一部分（`memory/write_policy.py`、`MemoryRepository` Port
及其内存实现），并在 ADR-0015 §5 登记了一条**已知边界**：

> 记忆写入与事件写入不在同一事务。

本 ADR 记录三件事：**那一处债务的闭合**、**为支撑它而做的结构决定**，
以及**本阶段明确没有做的事**。

## 1. 向量来自哪里：本地确定性实现（默认）+ OpenAI 兼容实现

### 事实

先用真实调用确认了两件事：

| 探测 | 结果 |
|---|---|
| DeepSeek `/v1/embeddings` | **404**——没有这个接口（社区结论一致） |
| 开发机上的中转站 `api.agnes-ai.cn` | 端点**存在**，但账户分组下**没有任何 embedding 渠道**：`text-embedding-3-small`、`bge-m3` 等一律 `503 model_not_found` |
| `api.openai.com` | 本机不可达（DNS 被污染，连接被拒） |

结论：**当前无法获得真语义向量**——这不是密钥问题，是环境限制。

### 决策

定义 :class:`~ai_psi.providers.embeddings.EmbeddingProvider` 协议，提供两个实现：

1. **`LocalHashingEmbedding`（默认）**——字符二元组 + 拉丁词，带符号的
   feature hashing 映射到 512 维，L2 归一化；
2. **`OpenAICompatibleEmbedding`**——`POST {base_url}/embeddings`，
   传输入层与对话 Provider 共用一套 HTTP 错误映射。

### 🔴 本地实现**不是语义向量**，这一点必须写进文档

它的余弦相似度近似于**词面重合度**：`简洁回答` 与 `用户偏好简洁回答` 得 0.655，
而 `简洁回答` 与 `完全无关的另一件事` 得 0.000——但对**同义改写**
（`喜欢简洁` vs `讨厌啰嗦`）几乎正交。

那为什么还要它：

* 它让 pgvector 的**全部真实机制**在没有外部服务的情况下就能跑通——
  固定维度、HNSW 索引、删除传播、版本兼容、`IS NOT DISTINCT FROM` 的
  空值语义——并且**被真实数据库上的测试钉死**；
* 它完全确定，测试里不需要任何 mock，也不会有间歇失败。

### 为什么外部实现也写了，尽管没跑通

它与对话 Provider **同构**：同一个 `/v1`、同一套 `map_http_error`、
同一份 JSON 处理。它的行为由 `httpx.MockTransport` 覆盖（含成功响应、
维度不符、条数不符、重复 index、各类 HTTP 错误）。

⚠️ **但"成功响应"这一条没有经过真实验证**——账户里没有 embedding 渠道。
这一点必须说清楚，不能让它看起来像是跑通过的：等渠道开通、
把 `AI_PSI_EMBEDDING_*` 配上，它就能用；在那之前，
它是一段**写好了但没被真实服务检验过**的代码。

（对照 ADR-0016 §1 为什么**不**写 Anthropic：那里缺的是**整个协议**，
连传输格式都没法验证；这里缺的只是一次真实响应——
端点在、错误格式对、参数形状与已跑通的对话接口一致。）

### 为什么用 blake2b 而不是内置 `hash()`

`hash("文本")` 对字符串**每个进程都不一样**——CPython 用 `PYTHONHASHSEED`
做哈希随机化。用它算向量的后果非常隐蔽：

* **同一个进程内**算出的向量彼此可比，测试全绿；
* 但**写入数据库的向量是上一个进程算的**，重启之后查询向量落在
  另一套随机桶里——检索**静默地全部失配**，不报错，只是永远查不到。

`tests/unit/test_embeddings.py::TestLocalDeterminism::test_across_processes`
用三个不同的 `PYTHONHASHSEED` 起子进程来钉死这条。

## 2. 向量单独一张表，而不是 `memories` 上的一列

### 决策

```
memories            —— 记忆本体（逻辑删除，行保留）
memory_embeddings   —— 向量索引（memory_id 主键 + 外键 ON DELETE CASCADE）
```

### 原因

不变量 15（"删除的记忆不得继续出现在向量检索结果中"）必须是
**结构性保证**，而不是"查询恰好带了过滤条件"。

若向量是 `memories` 上的一列：逻辑删除只把 `status` 改成 `deleted`，
行还在，**向量还在索引里**。检索正确与否完全取决于每一次查询都记得加
`WHERE status IN (...)`——漏一处就是隐私事故。而且 pgvector 的 HNSW
索引无法"只删一个向量"。

独立成表之后，"删除传播到向量索引"是一次**真实执行过的 DELETE**，
可以直接查表断言：

```sql
SELECT count(*) FROM memory_embeddings WHERE memory_id = :id
```

### 这换来了什么

两条同源的记忆可以有**不同的生命周期**：本体保存"曾经记过什么"
（审计需要），索引保存"现在能检索到什么"（能力需要）。
合成一个对象就必须二选一：要么丢掉审计轨迹，要么留下可检索的向量。

## 3. 记忆仓储挂进工作单元（闭合 ADR-0015 §5）

### 问题

阶段 3 的实现让 `MemoryService.correct` 的
"取代旧记忆 + 写入新记忆 + 写两条事件"跨在**三个事务**上。
它用"先做可能失败的操作、后写事件"的顺序把风险压小，但那只是压小：
事件写入失败会留下一次**改了却没记录**的纠正——
旧记忆已被取代、新记忆已写入，而事件流里查不到这件事发生过。

记忆的后果是累积的。这种"改都改了、却说不清为什么改"的状态，
比一次整体失败糟糕得多。

### 决策

`UnitOfWork` 协议新增 `memories: MemoryRepository`。
两个实现（内存 / PostgreSQL）都在工作单元内构造记忆仓储，
`MemoryService` 从 `uow.memories` 取用，不再单独注入仓储实例。

### 影响

* **契约测试的 fixture 形状统一了**：`memory_repository` 与
  `event_store`、`round_repository` 完全一样，不再是特例；
* `TestPostgresMemoryRepository` 这个阶段 3 留下的占位类**直接启用**，
  断言一行未改；
* `UnitOfWorkContract` 新增三条与记忆有关的断言
  （未提交即丢弃 / 提交后本体与索引都在 / 删除传播到索引）；
* `CognitiveRuntime` 依赖的从"记忆仓储"变成"记忆服务"——
  把仓储直接暴露出去，调用方就得自己管事务边界，
  而"自己管事务边界"正是这次要修的东西。

### 直接证据

`tests/unit/test_memory_service.py::TestAtomicity` 用一个
**一写事件就失败**的事件存储制造出那个中间态，断言：

* 写入路径失败时 `store.memories == {}` 且 `store.index == {}`；
* 纠正路径失败时旧记忆仍是 `ACTIVE`、版本没变；
* **删除路径失败时索引不能被清掉**——比"删了一半"更糟的是
  索引已移除、状态没改：那条记忆从此检索不到，
  而系统里没有任何地方显示它被删过。

## 4. 重复与冲突是两件事，确信程度差一个数量级

### 决策

| 检查 | 判据 | 动作 |
|---|---|---|
| **重复**（`find_exact_duplicate`） | 归一化后内容完全相同 + 类型相同 + 作用域相同 → **确定** | **拒绝写入** |
| **疑似冲突**（`find_potential_conflicts`） | 向量相似度超阈值 → **仅是线索** | 记入审计负载 |

### 原因

两者触发的动作不同：重复会**拒绝写入**，而拒绝是一个有代价的决定——
用户再次陈述同一件事时得不到任何反馈。用一个启发式的分数去驱动
一个有代价的动作，等于把"猜"当成"判"。

反过来，**冲突也绝不由这里判定**。"这两条记忆矛盾"是一个关于语义的
断言，而系统能算的只有"它们很接近"。把相似度高写成 `contradicts_ids`
是在**伪造一个事实**（任务书 §14 的不变量 3 正是要防止这类无根据的确定）。

因此线索进审计负载（`potential_conflict_ids`），
而 `contradicts_ids` 只接受**显式**关系（用户纠正、人工标注）。

### ⚠️ 阈值是针对本地向量标定的

`DEFAULT_CONFLICT_SIMILARITY_THRESHOLD = 0.75` 是在**归一化后的余弦**上取的
（`(cos+1)/2`）——余弦原始范围是 `[-1,1]`，直接用 0.75 当作阈值意味着
"夹角小于 41 度"，归一化之后是"夹角小于 60 度"，两者对同一份数据的
判定完全不同。换语义模型后**必须重新标定**：不相关文本的相似度普遍偏高，
同一个 0.75 会从"很接近"变成"随便两条都算"。

## 5. 审计不含正文，导出含正文

任务书 §10.5：**审计信息不得保留被删除内容正文。**

这条要求堵住了一个很自然的退路——"内容删了，但审计事件里留一份副本
方便日后追溯"。那样做的结果是：用户以为删掉的东西，
一直躺在**只追加**的事件表里，再也删不掉。

`memory/redaction.py` 提供两件互相对称的东西：

* `audit_payload_for_memory` —— 给审计用，**绝不含正文**；
* `export_record` / `export_bundle` —— 给用户用，**含正文**
  （导出本来就是把用户自己的数据交还给他）。

区分方式不是"记得别写错"，而是 `assert_audit_payload_safe`——
它在构造审计负载之后、写入事件之前执行，把"有没有夹带正文"
变成一条会当场失败的断言。

### 连哈希也不留

哈希是内容的**可验证承诺**：对取值空间很小的短句（"用户有抑郁症"），
持有哈希的人可以枚举候选逐个比对来还原原文。删除之后还留下这样一条线索，
与"内容真的不再存在"相差不远，但不是。因此只记 `content_length`。

### 导出要含被取代与已删除的记忆

用户要"导出我的数据"时，他有权看到完整的版本链——"为什么发生过修正"
正是靠这条链回答的。只导出有效记忆会让纠错痕迹凭空消失。

## 6. `memory/` 补齐的模块

| 模块 | 职责 |
|---|---|
| `retrieval.py` | 相似度、召回规模、零向量判定、词面重合度（**两个实现共用的纯函数**） |
| `ranking.py` | 综合排序：相关度 + 时效；冲突**不降权**；同分有确定的兜底 |
| `conflict_detection.py` | 重复（确定）与疑似冲突（线索） |
| `lifecycle.py` | 过期判定；保留策略的可读说明 |
| `redaction.py` | 审计脱敏与导出 |

**排序放在共享模块而不是各自实现**：契约测试只覆盖"能不能查到"，
不覆盖"为什么它排前面"。两边各写一份排序，"同一查询给出不同结果"
就会成为契约测试**看不到**的那类差异。

两个实现都采用**两段式**（先按向量召回 `recall_size(limit)` 条，
再综合排序），也是同一个理由：SQL 侧没法把整张表拉回来算余弦，
若内存实现全量参与排序，一个向量上排第 50、词面上完全匹配的记忆
会在内存里胜出、在 Postgres 里落选。

## 7. 本阶段明确没有做的事

### `GET /users/{user_id}/beliefs`（§12.3 第一条）

信念只活在事件流里，**不是记忆**；把它列出来需要另建一套判断投影，
那是另一件事。

这条暂缓由 `tests/api/test_api.py::test_beliefs_route_is_not_shipped_in_stage5`
钉住——让"暂缓"成为一个**可见的决定**，而不是一次遗漏，
否则它只会在阶段 8 验收时以"任务书里列了但没实现"的形式重新出现。

### 会话与 `RetentionPolicy.SESSION`

按会话失效需要"会话"这个 V0.1 里并不存在的一等对象。
`retention_requirements()` 因此**直说它尚未实现**——
导出是给用户看的，在那里说一句做不到的话，用户会据此做出错误的预期。

### 后台过期扫描

过期是**读时判定 + 显式维护调用**（`due_for_expiry`），
没有定时任务。理由：没有后台调度的情况下硬做一个"定时过期"，
只能靠某个请求顺带触发——那会让"什么时候过期"变成
"什么时候恰好有人请求"，时序不确定，排查时无从复现。

### 语义级反刍阈值（risks.md R32 的延续）

本阶段交付了向量检索的**能力**，但 `repetition_threshold = 0.85`
仍是词面标定。改它需要评测数据（阶段 7）。

### ⚠️ V0.1 没有认证层

`user_id` 由调用方显式声明。作用域过滤**防的是"代码写错导致的串号"，
不是"恶意调用者"**：它确实挡住了真实的一类缺陷（检索忘记带作用域、
纠正打错用户），但挡不住一个故意传入别人 user_id 的调用方。

这条边界写进了 `api/routes/memories.py` 的模块文档与 risks.md R40，
而不是留给读者从"为什么 user_id 是个参数"里自己推断。

## 替代方案与取舍

| 方案 | 为什么不选 |
|---|---|
| 只做本地向量，不写外部实现 | 换 Provider 会变成"写一个新模块"，而不是"改两行配置" |
| 只做外部实现 | 本机拿不到 embedding 渠道，交付的将是一段无法验证的代码 |
| 向量作为 `memories` 的一列 | 不变量 15 退化成"查询恰好带了过滤条件"；HNSW 也无法只删一个向量 |
| 记忆仓储保持独立 Port | 修正记忆的四个步骤继续跨三个事务（ADR-0015 §5） |
| 用相似度同时做重复与冲突判定 | 用启发式分数驱动一个"拒绝写入"的有代价动作 |
| 把相似度高的写成 `contradicts_ids` | 在伪造一个关于语义的事实（不变量 3） |
| 审计里保留内容哈希 | 短文本的哈希可被枚举还原 |
| 导出只含有效记忆 | 纠错痕迹凭空消失，"为什么发生过修正"无从回答 |
| 阶段 5 顺手实现 `/beliefs` | 信念不是记忆，需要另建判断投影——那是另一件事 |
| 给向量 Provider 套熔断 | 熔断只会让写入更快失败，不会让它更可能成功 |

## 影响

- `UnitOfWork` 协议新增 `memories`；两个实现同步。
- `MemoryRepository` 协议新增 `indexed_ids()`——**它不是测试钩子**，
  而是不变量 15 唯一可被直接观测的形式。
- `make_unit_of_work_factory` / `make_in_memory_unit_of_work_factory`
  新增 `embeddings` 参数（**无默认值**：隐式默认会让声明的版本
  与仓储实际算出的版本悄悄分家）。
- `CognitiveRuntime` 的 `memory` 依赖改为 `memory_service`。
- `MemoryService` 改为从 `uow.memories` 取仓储；新增
  `export_user_data` / `delete_user_data` / `reindex` / `conflicting_memory_ids`；
  `delete` 返回 `MemoryDeletion`。
- 新增包内模块：`providers/embeddings.py`、`memory/{retrieval,ranking,conflict_detection,lifecycle,redaction}.py`、
  `infrastructure/db/memory_repository.py`。
- 新增两张表与一条迁移（含 HNSW 索引、`CREATE EXTENSION vector`）。
- 新增事件类型 `memory.exported`（33 → 34）。
- `Settings` 新增 `embedding_provider` / `embedding_dimension` /
  `embedding_model` / `embedding_base_url` / `embedding_api_key`。
- 新增五条 API 路由（§12.3）。
- 新增依赖 `pgvector`（Python 包，仅提供 SQLAlchemy 的 `Vector` 类型；
  它返回 `list[float]`，**不依赖 numpy**）。
