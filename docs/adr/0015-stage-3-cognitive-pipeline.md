# ADR-0015：阶段 3 认知流水线的实现决策与偏差登记

- **状态**：已接受
- **日期**：2026-09-18
- **相关**：ADR-0003（Provider 抽象）、ADR-0008（深度路由与预算）、
  ADR-0009（内存适配器）、ADR-0012（V0.1 范围边界）、ADR-0013（持久化）

## 背景

阶段 3 交付"Mock LLM 与认知流水线"，验收条件是
**不使用外部 API 也能完整运行、场景 A–J 全部通过、循环永不超预算**。

阶段 0/1/2 定下的是**接口与边界**；本阶段第一次把它们接起来跑通，
于是暴露出若干"设计时无法判断、实现时才有答案"的问题：

* 哪些模块真的需要模型调用？
* 预算表在真实模块成本下还够不够用？
* 状态机的转移表是否覆盖了所有真实路径？
* 两个存储实现（内存 / PostgreSQL）的语义是否真的一致？

本 ADR 记录这些问题的结论。**它同时是一份偏差登记表**——
凡与阶段 0 文档（尤其是 `docs/prompt_contracts.md`）不一致之处，
都在第 3 节列出。

---

## 1. 模块分层：哪些是模型调用，哪些是代码

阶段 0 的 `docs/prompt_contracts.md` 按任务书 §9 的章节顺序列出了 13 个 Prompt 任务。
实现时逐项复核"这件事真的需要模型吗"，结论是 **11 个模型任务 + 2 个确定性模块**。

### 1.1 `response_planner` 改为确定性代码

任务书 §9.12 要求 Planner 决定：应直接回答什么、哪些不确定性要告诉用户、
是否需要展示替代解释、哪些内部候选不应表达、是否需要澄清、回答长度和深度。

**这六项全部可以从 `Judgment` 与 `Reflection` 直接读出来。**
让模型来决定"要不要表现得确定"，等于让被约束方自己执行不变量 7。
放在代码里，不变量 7 就从"事后抽查"变成了"结构性成立"。

唯一需要判断力的是"哪些候选不该说"，那也有明确规则：没有证据支持时，
不向用户呈现关于第三方心理动机的推断（§9.1、场景 B）。

### 1.2 `epistemic_analyzer` 改为确定性代码

任务书 §9.4 要求把上下文分为八类。这八类**完全可以从材料的元数据推出来**：
信任等级、核验状态、时效性、直接性、是否被取代、是否冲突。

把结构化元数据交给模型重新分类，既多花一次调用，又引入了一个可能出错的环节——
模型完全可能把一条 `VERIFIED` 的证据说成 `TENTATIVE`，而代码不会。
§9.4 的另一条要求"不得只给置信度，必须说明依据类型"反而**只有代码能如实满足**：
依据就是元数据本身。

### 1.3 `hypothesis_evaluator` 改为确定性代码

让同一个模型既提出假设、又给假设打分，是确认偏差的标准配方。
评估要做的事很机械——"这条假设有几条证据支持、几条反对"——
可以从证据关系算出，且结果可复现、可审计。

### 1.4 `depth_router` 保持纯规则（无模型调用）

任务书 §7.3 的措辞是"优先使用确定性规则，再允许模型建议"。
本实现取更严格的一半：**模型只提供深度信号**（关于问题性质的事实判断），
路由规则完全在代码里（ADR-0008 已有决策）。

**净效果**：11 个 Prompt 任务，与 `docs/prompt_contracts.md` §3 相比少一个
（`response_planner`），且新增了 `docs/prompt_contracts.md` 里列为"全部深度"的
`epistemic_analyzer` 不再需要契约。

## 2. 预算表按实测重新标定

阶段 1 写下的 `max_model_calls = 3/5/8/11/12` 是**估算**。
阶段 3 实现模块矩阵后逐档核算，得到真实标称值：

| 深度 | 标称模块数 | 一次额外循环 | 需要的预算 | 旧值 → 新值 |
|---|---|---|---|---|
| D0 | 4 | 0（无元认知） | 4 | 3 → **4** |
| D1 | 6 | 0（循环上限 1） | 6 | 5 → **6** |
| D2 | 8 | 2 | 10 | 8 → **10** |
| D3 | 10 | 2 | 12 | 11 → **12** |
| D4 | 11 | 2 | 13 | 12 → **13** |

不变式（由 `tests/unit/test_orchestrator_and_depth.py` 断言）：

```
max_model_calls ≥ 标称模块数 + (max_metacognitive_loops − 1) × 2
```

**差一次调用就意味着反刍检测永远等不到第二次复核来比较两轮判断**，
而任务书 §13.3 的防反刍正是建立在"连续两轮"之上。

任务书 §13.1 的默认值 12 是全局默认；§13.1 同时明确"允许按 D0～D4 配置不同预算"。
D4 的 13 因此不构成偏差。

**同时删除了 `Settings` 里的六个 `budget_max_*` 字段**——它们没有任何读取方，
是死配置。死配置比没有配置更糟：它看起来可调，却不会有任何作用。
预算的权威表只有 `_BUDGET_BY_DEPTH` 一处。

## 3. 状态机与事件模型的两处补齐

### 3.1 D0 也必须经过元认知复核（规则层）

状态机**不允许** `DELIBERATING → SYNTHESIZING` 直达——
"合成之前必须经过元认知复核"是转移表的明确意图。

D0 的 `max_metacognitive_loops = 0`，因此它进入 `METACOGNITIVE_REVIEW`
但**只跑规则层**（零模型调用），照样留下一条"为什么停下来"的决策记录（不变量 19），
`stop_reason = DIRECT_ANSWER`。

同理，**预算不足以再问一次模型时也走规则层复核**，
`stop_reason = BUDGET_CONSTRAINT`——规则层永远可用，因为它不花钱。

### 3.2 新增事件类型 `cognition.analysis.completed`

任务书 §9 描述了逻辑/因果/辩证/哲理四个分析模块，§5.2 的 32 条事件清单里
却**没有任何一条与之对应**。缺了它，这些模块的模型调用就**没有地方记录**
`model` 与 `prompt_version`——**直接违反不变量 18**。

这是与 `cognitive_round.cancelled`（ADR-0012）同一类缺口：
清单与模块清单不同步。事件类型总数 32 → 33。

### 3.3 终态事件现在真的被发出

任务书 §5.2 列出了 `cognitive_round.completed` / `failed` / `suspended` / `cancelled`
四种事件，但阶段 2 把**全部**转移统一写成 `cognitive_round.state_changed`，
这四种类型从未被发出——是死的词汇表。

只有 `state_changed` 的话，"找出所有失败的回合"必须解析每条事件的负载。
现在终态会**额外**写一条具名事件（同一事务内），
`state_changed` 保留不变，回放的统一性不受影响。

## 4. 契约测试发现的两处实现不一致

按 ADR-0009，阶段 3 为存储 Port 写了契约测试，**同一组断言跑两个实现**。
它当场抓到两处 PostgreSQL 实现与契约不符的地方——**这正是它存在的理由**：

1. **`SqlAlchemyEventStore.append_many` 泄漏了 `sqlalchemy.exc.IntegrityError`。**
   契约说"重复 id 抛 `ConflictError`"，调用方就按 `ConflictError` 写 `except`。
   把基础设施异常透出去，那些 `except` 会静默失效。
   已修：捕获唯一约束冲突并转换为 `ConflictError`。

2. **`SqlAlchemyIdempotencyStore.bind` 在 key 从未占位时静默成功。**
   后果不是"少做一件事"，而是这个幂等键永远停在"已占位未绑定"状态，
   此后每次重试都得到 `CONFLICT` 而不是 `REPLAY`——
   用户看到的是"重试永远失败"，而根因（一次错误的调用顺序）没有任何地方记录。
   已修：受影响行数为 0 时抛 `ConflictError`。

这两处**都不是阶段 3 引入的缺陷**——它们一直存在，
只是在有了第二个实现之前无从对照。

## 5. 记忆的接线方式（阶段 3 的边界）

`MemoryRepository` **不是** `UnitOfWork` 的一部分，而是独立注入的 Port。
理由：它的每个方法自身就是一次原子操作，阶段 5 的 PostgreSQL 实现同样如此
（各自一个事务）。把它塞进 `UnitOfWork` 反而会让两个实现在
"事务边界在哪"这件事上产生差异——而契约测试正是用来防止这种差异的。

**已知边界**（阶段 5 闭合）：`MemoryService.correct` 的
"取代旧记忆 + 写入新记忆 + 记录事件"在阶段 3 **不是跨表原子的**。
实现上用"先做可能失败的操作、后写事件"的顺序把风险压到最小。

**存储后端的组合**（`AI_PSI_STORAGE_BACKEND`）：

| 取值 | 事件 / 回合 / 幂等 | 记忆 |
|---|---|---|
| `memory` | 内存 | 内存 |
| `postgres` | PostgreSQL | **内存** |

`postgres` 下的记忆仍走内存实现是**刻意的**：记忆表要到阶段 5 才建。
这个混合让"认知闭环已经跑通"可以在真实数据库上验证，
同时不会假装记忆已经持久化。

## 6. API 的三处如实说明

1. **`POST .../messages` 同步执行整个回合**，响应的 `status` 是**真实终态**，
   而不是任务书 §12.1 示例里的固定值 `"CREATED"`。
   V0.1 没有后台任务队列（那是阶段 4 之后的事），
   返回一个必然已经过期的 `"CREATED"` 只是照抄示例。
2. **`POST /conversations` 只生成一个 UUID**，并在响应里说明
   "会话是客户端分组键，服务端尚未持久化会话实体"。
3. **只实现 §12.1 与 §12.5**。`memories` / `feedback` / `proposals` / `beliefs`
   依赖阶段 5/6 才交付的能力，**本阶段不建空壳**（ADR-0012）；
   有测试断言这些路由现在不存在。

## 7. 反向断言（Pydantic）的一个使用注意

`model_copy(update=...)` **不跑校验器**。
用它构造"应当被拒绝的值"会让测试变成空转——
第一版 `test_rollout_other_than_one_is_rejected` 就是这么写的，已改为重新构造。
把它写在这里是因为这个坑很容易再踩一次。

## 替代方案与取舍

| 方案 | 为什么不选 |
|---|---|
| 把响应规划交给模型 | 不变量 7 会退化成"模型自己承诺" |
| 把认知状态分类交给模型 | 元数据分类是机械工作，模型只会引入出错环节 |
| 让模型同时生成与评估假设 | 确认偏差的标准配方；且评估结果不可复现 |
| 保持阶段 1 的预算数字 | 会逼着编排器在运行期"少跑一个模块"，反刍检测因此永远不触发 |
| 让 D0 跳过元认知状态 | 状态机不允许 DELIBERATING → SYNTHESIZING 直达 |
| 保持只有 state_changed 事件 | 任务书列出的四种终态事件会成为死词汇表 |
| 把记忆塞进 UnitOfWork | 两个实现的事务边界会对不齐 |
| 在阶段 3 就建记忆表 | 那是阶段 5 的交付物；提前建表会把"记忆策略尚未定型"的风险带进来 |

## 影响

- `Settings` 少六个字段；新增 `storage_backend` 与 `repetition_threshold`。
- `CognitiveBudget._BUDGET_BY_DEPTH` 的四个数字变化，同步修改 ADR-0008。
- `EventType` 从 32 条变为 33 条。
- `UnitOfWork` 协议不变（**没有**加入 `memories`）。
- 新增包：`providers/`、`prompts/`、`reliability/`、`memory/`、`api/`；
  `cognition/` 补齐 15 个模块；`application/` 新增
  `cognitive_runtime.py` / `artifact_service.py` / `memory_service.py`。
- 新增测试：契约（两个实现）、场景 A–J、API、Prompt 契约与注入防护。
