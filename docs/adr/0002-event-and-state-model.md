# ADR-0002：事件与状态模型

- **状态**：已接受
- **日期**：2026-09-17
- **相关**：ADR-0001（架构风格）、`docs/state_machine.md`

## 背景

系统必须回答"系统知道当前在思考什么"和"为什么继续/为什么停止"。
任务书 §5.2 定义了 `Event`，§六定义了 14 个认知回合状态，
§13.4 要求幂等与乐观锁，§14 要求"状态机不得跳过禁止跳过的状态"。

核心问题是：**事件与状态谁是真相来源？**

## 决策

采用 **事件记录 + 当前状态投影（Event Log + State Projection）** 的折中模型，
而非纯事件溯源。

**具体规则：**

1. **事件只追加，永不修改、永不删除。**
   任何认知产物（Observation / Hypothesis / Judgment / Memory / …）的产生与变更
   都写入对应事件。事件是审计与回放的依据。

2. **当前状态作为投影单独存储**，用于查询与并发控制。
   `CognitiveRound` 等聚合有物化的当前状态行，带 `version` 字段做乐观锁。

3. **事件与投影在同一事务中写入。** 不允许只写其中一个。
   事务失败则两者都不落库（任务书："事务失败不会留下半成品数据"）。

4. **禁止静默覆盖。** 修改领域对象必须：
   - 递增 `version`（乐观锁，冲突则拒绝写入并报错，不重试覆盖）
   - 产生一条对应事件
   - 重要对象保留历史版本（如 `Memory.supersedes_id`、`Belief.supersedes_id`）

5. **回放不覆盖原始事件。**
   回放是只读的重演，产物写入独立的回放结果，不修改历史。

6. **失败不破坏已写入事件。**
   回合进入 `FAILED` 时，此前已提交的事件保持有效；失败本身也记录为事件
   （`cognitive_round.failed`），并必须携带失败阶段与错误类别。

**关于"纯事件溯源"的取舍：** 纯 ES 需要每次查询都重放事件流，
或维护复杂的快照与重放版本兼容逻辑。V0.1 的规模不值得这个复杂度，
但保留完整事件日志意味着**未来若需要，可以无损迁移到纯 ES**。

## 替代方案与取舍

| 方案 | 为什么不选 |
|---|---|
| 纯事件溯源（无状态表） | 查询需重放，复杂度与性能代价高；V0.1 收益不足 |
| 纯状态表（无事件日志） | 直接违反任务书"重要对象保留变更事件"与"可追踪"的核心要求 |
| 事件日志 + 定期快照 | 快照与事件的一致性处理是额外复杂度；V0.1 查询量不需要 |
| 用数据库触发器写事件 | 把领域逻辑泄漏到数据库层，违反 ADR-0001 的依赖规则 |

## 影响

- 事件表将是增长最快的表，需要索引策略（阶段 2 处理）。
- 所有写路径必须经过 `application/` 层，以保证事件与投影成对写入。
- 乐观锁冲突是**正常业务路径**，不是异常：API 层需返回可重试的明确错误。
- 幂等键（Idempotency-Key）在应用层实现，防止 API 重试创建重复回合。
