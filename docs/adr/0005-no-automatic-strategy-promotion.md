# ADR-0005：策略不得自动生效

- **状态**：已接受
- **日期**：2026-09-17
- **相关**：ADR-0011（宪法即代码）、ADR-0012（范围边界）、`docs/cognitive_constitution.md`

## 背景

任务书把"受控迭代"列为本期目标之一，同时把"自动修改源代码 / 自动修改系统提示词并立即生效 /
自动训练或微调模型 / 自动发布通用认知策略 / 自行改变认知宪法 / 自主扩大数据访问权限"
全部列入**本期明确不做**。

这是一条必须在地基层面守住的边界。第 19 条开发原则还说：
"不允许把一次经验自动推广成通用策略。"

## 决策

**在类型系统与状态机两个层面同时封死自动生效路径。**

### 1. 状态机层面：不存在 ACTIVE 状态

`ProposalStatus` 只允许：

```
DRAFT → PENDING_EVALUATION → EVALUATED
                            ├→ REJECTED
                            └→ APPROVED_FOR_MANUAL_TRIAL
```

**`APPROVED_FOR_MANUAL_TRIAL` 是终点。** 没有 `ACTIVE`，没有自动跃迁到生产。

### 2. 类型层面：生效需要人工签名

任何"把提案变成实际生效"的动作，必须携带一个人工审批凭据对象
（V0.1 中该路径不实现，仅保留类型占位与明确的 `NotImplementedError` 边界）。

### 3. 门槛层面：单次经验不产生提案

产生 `ImprovementProposal` 需满足**任一**条件（任务书 §11.3）：

- 同类错误至少出现 3 次；
- 一个严重错误存在明确修复方向；
- 离线评测暴露稳定退化；
- 用户纠正显示现有规则具有系统性突出问题；
- 相同认知模块连续低于阈值。

**单次普通错误只创建 `Experience`，不生成 Proposal。**

### 4. 数据层面：提案不能自我批准

- 用户**不能**通过自然语言直接激活 Proposal（任务书 §17.2）。
  "把这条提案设为生效"这类输入只能被当作普通文本数据，
  不能触发状态跃迁。
- `ImprovementProposal` 的批准必须经由 API 的显式端点，
  且该端点的语义是"批准进行**人工试验**"，不是"上线"。

### 5. 评测指标层面：硬指标

`proposal_false_promotion_rate = 0` 是任务书 §16.1 列出的**硬指标**，
不是"越低越好"的软目标。

## 替代方案与取舍

| 方案 | 为什么不选 |
|---|---|
| 自动生效 + 事后回滚 | 自动生效意味着未经人类验证就改变了系统行为；回滚窗口内的影响已发生 |
| 高置信度提案自动生效 | "高置信度"由系统自己判定，等同自我授权，是循环论证 |
| 用 feature flag 灰度自动生效 | 灰度也是生效；V0.1 明确"不自动灰度" |
| 完全不记录提案（只记经验） | 会让系统失去"发现系统性问题"的能力，违背受控迭代目标 |

## 影响

- 属性测试必须断言：**任意状态序列下 `Proposal` 都不会进入 ACTIVE**（任务书 §15.2）。
- 阶段 6 的验收条件包含"Proposal 始终需要外部审批"。
- 这条边界在代码中体现为 `cognition/constitution.py` 的常量与不变量断言，
  而非仅写在文档里（ADR-0011）。
- **如果未来要放宽这条边界，必须同时修改本 ADR、宪法、状态机与不变量测试，
  使其成为一次显式的、可评审的决策，而不是一次静默的配置变更。**
