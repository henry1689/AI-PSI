# ADR-0021：输入契约与事务原子性（阶段 6.5 §三）

- **状态**：已接受
- **日期**：2026-09-18
- **相关**：ADR-0002（事件与状态）、ADR-0004（记忆策略）、ADR-0014（跨平台与测试库）、
  ADR-0015（阶段 3 实现决策）、ADR-0018（反馈、经验与提案）、
  ADR-0020（经验评价与独立性语义）

## 背景

阶段 6.5 §三 提出的是一类**横切问题**：同一件事在不同层、
不同后端上的答案不一致。它点名了四类：

1. **输入规则不统一**——某些空白被挡、某些被放行，取决于用的是
   `strip()` 还是 `len()`；
2. **错误码不可机器读**——FastAPI 默认的 422 只有 `detail`，没有 `code`；
3. **非法输入被报成服务端故障**——用户输入触发的 500；
4. **部分提交**——反馈留下了、它应该带出的记忆或经验评价没留下。

本 ADR 记录四组决定，其中第一组**推翻 ADR-0018 §4 的一处刻意设计**。

---

## 1. 事务原子性：反馈、经验评价、记忆更新同事务

### 阶段 6 的原设计（ADR-0018 §4，本次修正）

> 反馈事件先落，记忆更新后做，两步不在同一个事务里。
> 反过来（记忆先写、事件后记）的失败后果是"改了却没有记录"——
> 但在这里，另一个方向的失败更严重：**用户说过的话丢失了**。

### 本次决定

三者改为**同一事务**。理由不是"阶段 6 想错了"，而是**事实变了**：

阶段 6 时反馈路径只产出两样东西（反馈事件、记忆）。
阶段 6.5 起它产出**三样**——还多了一条 `experience.evaluated`
（ADR-0020）。三者表达的是**同一件事**："用户此刻指出了这个回合的问题"。
分成两个事务之后，"纠正留下了、它应该抬高的经验没抬高"会让
**门槛永远跨不过去**，而且没有任何报错——表现只是"链路说没有提案"。

### 那条顾虑由什么承接

它没有被丢掉，改由两条机制承接：

| 机制 | 覆盖的情形 |
|---|---|
| **写入策略拒绝是正常返回，不是异常** | 反馈内容命中红线。策略拒绝、事务**照常提交**，反馈与经验评价都留下，只有记忆没写。**这是最常见的情形** |
| **真正的数据库故障整体回滚** | 反馈确实会丢。这是"同一事务"的固有代价——原子性与"某个子步骤失败时仍保留其余部分"在定义上互斥 |

区别在于：现在这个代价是**写在 ADR 里、被选择过的**，
而不是两事务方案里那个没有被讨论过的副作用。

> ⚠️ ADR-0018 §4 的原文**不修改**（ADR 规则）。本节是它的修正记录。

### 实现

`MemoryService.propose` 新增可选参数 `uow`：非空时调用方拥有事务，
本方法不提交。反馈路径把它的工作单元交进去，
记忆写入因此长在反馈的事务上。

写入策略的判定与"没有重复"的判定都在同一个事务里——
后者对调用方的事务同样成立，而且更强：重复检查、结论、
以及那条记忆的落库全部发生在同一个事务里。

## 2. 输入规则统一：**一种空白**

### 事实

`str.strip()` 用的是 Unicode 的 `White_Space` 属性，
而零宽空格（`U+200B`）属于**格式字符**（`Cf`）——`isspace()` 对它返回 `False`。

后果：一个只由零宽字符组成的字符串

- 长度不为 0 → 穿过 `min_length=1`；
- `strip()` 之后不为空 → 穿过 `str_strip_whitespace`；
- 于是**落进只追加的事件流**——它看起来是空的，占着位置，检索不到，
  而且删不掉（事件表没有 DELETE 路径）。

同时它还**穿透了另一条路径**：`MemoryService` 的空白检查当时写的是
`not content.strip()`，同样放行。

### 决定

定义 `ai_psi.domain.common.is_blank(text)`，判据是
**"去掉 Unicode 空白与 :data:`INVISIBLE_CHARACTERS` 之后还剩下什么"**。

集合用**码点**列举，刻意不含方向控制符（`U+202A`–`U+202E`）与
变体选择符（`U+FE00`–`U+FE0F`）：前者出现在正文里是一种真实
（虽然可疑）的表达，后者是 emoji 的一部分——把它们一起抹掉
会改变**有内容**的输入。

🔴 **源码里不出现任何不可见字符。** 用 `chr(code_point)` 生成。
把不可见字符直接写进源码，会让这个集合本身变成一段**看不见的代码**：
评审时无从检查，编辑时容易连同注释一起被误删。

🔴 **HTTP 边界与服务层用的是同一个函数。** 两处各写一份的话，
"什么算空白"会在边界与领域层给出不同答案——而两处各自都是自洽的，
没有任何测试会自然发现。

应用点：`SubmitMessageRequest.content`、`CorrectMemoryRequest.new_content`、
`FeedbackRequest.content`、`RejectProposalRequest.reason`、
`EvaluateProposalRequest.evidence`（逐条）、`WritePolicy`、
`ProposalGate.review`。

### 附带修好的一处

`SubmitMessageRequest` 此前用的是 `_STRICT`（**不** strip），
因此 `content="   "` 能启动**一整个认知回合**——白花一次预算。
现在它用 `_STRICT_TRIMMED` 加空白校验。

## 3. 长度上限：没有上限不是"宽松"，是一条存储耗尽通道

### 事实

阶段 6.5 之前，所有自由文本字段**没有上界**：
`content`、`reason`、`note`、`related_claim`、`evidence` 的每一项。

它们进的是**只追加**的事件表（没有 DELETE 路径），
而反馈正文还会进记忆。一个请求就能往一个删不掉的地方写任意多字节。

### 决定

| 常量 | 值 | 用于 |
|---|---|---|
| `_FREE_TEXT_MAX` | 8 000 | 用户消息、反馈正文、记忆内容 |
| `_NOTE_MAX` | 2 000 | 驳回理由、批准说明、单条对照口径 |
| `_LIST_MAX` | 50 | `evidence` 的条目数 |
| `_ACTOR_ID_MAX` | 128 | 与事件表的 `varchar(128)` **对齐**（阶段 6 已定） |

值远大于任何真实输入（8000 字符约等于一篇长文），
因此它约束的是滥用，不是用法。

🔴 **上限必须 ≤ 数据库列宽。** 阶段 6 真的出过一次由此产生的缺陷：
`actor_id` 超过 128 时，内存后端返回 201、PostgreSQL 返回 **500**——
**同一个 HTTP 契约，两个后端两个结果**。

## 4. 错误响应：机器可读的 `code`，且不回显输入值

### 决定

新增 `RequestValidationError` 处理器。FastAPI 默认返回
`{"detail": [...]}`——没有 `code`，客户端要区分"字段缺失"与"值非法"
只能解析那句会随 pydantic 版本变化的英文消息。

现在返回：

```json
{"code": "invalid_request", "message": "请求格式或取值不合法",
 "fields": ["body.evidence.0"]}
```

🔴 **`code` 与 `InvalidRequestError.default_code` 是同一个值。**
两者都表示"这次请求的输入不合法"，区别只在**哪一层发现的**。
给它们两个不同的码，会让客户端必须知道"服务端把这类校验放在哪一层"
才能正确处理错误——而那是一个实现细节，不该泄漏到契约里。

🔴 **响应里只回字段路径，不回输入的值。**
pydantic 默认的 `detail` 含 `input`——那是**用户原文**。
把它原样回显会把一次"格式错误"变成一次 XSS/日志注入的载体，
而且错误响应是最容易被完整记录下来的东西之一。

## 5. 安全审计通道：独立于领域事件流

### 决定

新增 `ai_psi.infrastructure.security_audit`，走独立的
`ai_psi.security` logger。**只写结构化日志，不写数据库、不参与任何事务。**

理由是一个被拒绝的请求有两个特征，恰好与领域事务不相容：

1. **它没有回合、没有用户、没有关联链。** 往领域事件流里写它，
   就要么伪造这些字段（那是在审计记录里撒谎），要么让它们为空
   （那会让"这个回合发生了什么"的查询多出一堆无关的行）；
2. **它不该有能力影响任何领域事务。** 请求被拒绝的原因可能是
   恶意的、畸形的、或超长的——让这样一个输入参与事务，
   等于给它一个"让别人的写入回滚"的机会。

### 记什么

| 记 | 不记 |
|---|---|
| 路径、方法、错误码 | 请求正文 |
| **出错字段的路径**（`body.evidence.0`） | 字段的**值** |
| | 任何用户原文片段 |

🔴 只记字段路径不记值：被拒绝的输入里最常见的正是
"不该被存下来的东西"——把它的值记进日志，
等于用一个拒绝动作完成了那次本被拒绝的写入。

字段路径最多记 20 条，且**截断本身被记录**（`field_path_overflow`）：
只报前 20 条而不说明"还有多少条"，会让一次千字段的畸形请求
在审计里看起来只是一次普通的 20 字段错误。

## 6. 裸异常的边界

阶段 6.5 §三.4 要求"服务层遇非法输入应抛出专用领域异常，
不使用裸 `ValueError` 表达不变量"。

本 ADR 明确这条要求的**范围**：

| 位置 | 裸异常 | 判断 |
|---|---|---|
| `PatternDetector(threshold=1)` 等**构造参数**校验 | `ValueError` | ✅ 保留。这是**编程错误**，不是用户输入；Python 里构造参数用 `ValueError` 是惯例，且它们从 API 不可达 |
| `Reviewer._require_judgment()` 等**阶段顺序**保证 | `RuntimeError` | ✅ 保留。`# pragma: no cover`，由流水线顺序保证，客户端不可达 |
| `dependencies.get_container()` 容器缺失 | `RuntimeError` | ✅ 保留。说明没走 `create_app`，是部署错误 |
| **服务层的用户输入校验** | — | 🔴 **必须**用 `InvalidRequestError` 等专用领域异常 |

判据不是"哪个函数在哪一层"，而是**"这个非法值能不能来自客户端"**。
能来的，就只能是领域异常——否则它会以 500 的形式抵达用户。

## 影响

- 反馈路径的 `FeedbackOutcome` 新增 `evaluations` 字段：
  本次反馈**实际改变**了哪些经验的评价。空元组与"改了几条"
  必须能区分——前者可能是"反馈类型本就不携带这个信息"，
  也可能是"目标经验的档位已经更高"，理由里会说清是哪一种；
- **契约测试现在跑在两个后端上**（`tests/integration/test_input_contract.py`）：
  26 条用例 × 2 个后端。这是阶段 6.5 能力矩阵里"交集为空"那个缺口的
  第一块填补，也是 §三.9"最终验收只以真实 PostgreSQL 结果为准"的落点；
- 空白与长度规则**集中在一处**（`domain/common.is_blank` 与四个常量），
  新增字段时忘了加校验仍然可能——因此 §七 的黑盒验收把它列为必测项；
- **残余风险**：`evidence` 的长度校验写在 Schema 校验器里而不是
  `Field(max_length=...)`，因为它是**逐项**的（pydantic 的 `max_length`
  对 list 管的是长度不是各项）。两处写法不一致，改动时容易只改一处。
  登记在 risks 中。
