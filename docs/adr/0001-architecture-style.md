# ADR-0001：架构风格

- **状态**：已接受
- **日期**：2026-09-17
- **相关**：ADR-0002（事件与状态）、ADR-0009（内存适配器）、`docs/architecture.md`

## 背景

任务书要求这个系统"不是普通聊天机器人"，而是可追踪、可测试、可纠正的认知运行时。
它必须支持：结构化认知产物、事件记录、状态流转、证据关系、元认知控制、
长期经验、受控迭代提案。

同时明确要求：**大模型是可替换组件，领域逻辑不能依赖特定供应商**；
**V0.1 不引入 Kafka、Kubernetes、Neo4j 等重型基础设施**。

这两条合起来约束了架构风格的选择：需要清晰的对象边界与依赖方向，
但不能用重型基础设施换取的复杂度。

## 决策

采用 **轻量 DDD + 事件记录 + Ports and Adapters**：

```
┌─────────────────────────────────────────────────────────┐
│  api/  (FastAPI)          ← 适配器（阶段 3 起）          │
├─────────────────────────────────────────────────────────┤
│  application/  (应用服务)  ← 唯一允许发起写入的地方       │
├─────────────────────────────────────────────────────────┤
│  cognition/  learning/  memory/  reliability/            │
│      ← 领域逻辑：纯规则、纯函数优先，不依赖 IO            │
├─────────────────────────────────────────────────────────┤
│  domain/  (领域对象)       ← 零依赖，只依赖 pydantic      │
├─────────────────────────────────────────────────────────┤
│  providers/  infrastructure/  ← Ports 的具体实现          │
└─────────────────────────────────────────────────────────┘
```

**四条硬性依赖规则：**

1. `domain/` **不依赖任何其他包**（除 pydantic），不做 IO、不含 async。
2. `cognition/` 等领域的编排逻辑通过 **Protocol（Port）** 访问外部世界，
   不直接 import `infrastructure/` 或 `providers/`。
3. **只有 `application/` 允许发起持久化写入。** 模型永远不能直接写数据库。
4. 依赖方向永远向内：外层知道内层，内层不知道外层。

**明确不引入：** Kafka、Kubernetes、Neo4j、Celery、Redis（V0.1 阶段）。
异步任务先用数据库队列（阶段 2 起）。

## 替代方案与取舍

| 方案 | 为什么不选 |
|---|---|
| 分层 MVC 单体 | 无法强制"模型不能直接写库"和"领域不依赖供应商"这两条硬约束 |
| 完整 DDD（聚合根、领域事件总线、仓储接口全套） | V0.1 的规模撑不起，属于规则 2 禁止的"推测性抽象" |
| 纯函数式管道（无对象） | 任务书要求"所有重要认知产物必须是结构化对象"，且需要乐观锁与版本 |
| 微服务 | 明确被任务书排除（重型基础设施） |
| 事件溯源（Event Sourcing）全量 | 状态重建复杂度高；V0.1 采用"事件记录 + 当前状态投影"的折中（见 ADR-0002） |

## 影响

- **正面**：领域对象可独立测试，无需数据库；Provider 可替换；写入路径唯一，便于审计。
- **代价**：需要为每个外部依赖定义 Protocol，初期有样板代码。
- **约束**：阶段 1 只建立 `domain/` 与 `cognition/`，其余包在对应阶段引入，
  不预先创建空壳目录（见 ADR-0012）。
- **对测试的影响**：场景测试（任务书 §15.4）可以完全用内存适配器跑，
  不依赖 PostgreSQL 或任何外部 API。
