# 风险清单

> 相关：`docs/implementation_plan.md`、各 ADR
> 更新：每阶段结束复核一次

---

## 1. 认知风险（最高优先级）

这类风险的特殊之处：**后果是累积的**。
一次错误回答只影响一次交互；一次错误的记忆写入会持续影响此后所有回合。

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| **R1** | **记忆污染**：错误信息被写入长期记忆 | 持续污染后续所有回合，且用户难以察觉 | WritePolicy 白名单 + 默认拒绝（ADR-0004）；`memory_write_rejection_rate` 作为观测指标 |
| **R2** | **跨用户泄漏** | 隐私事故，不可撤销 | `user_id` 作用域为必填参数（无默认值）；属性测试断言（硬指标 = 0） |
| **R3** | **删除未传播到向量索引** | "已删除"的记忆仍可被检索出来 | 删除必须同时作用于主表与索引；阶段 5 专项测试 |
| **R4** | **过度自信**：回答比内部判断更确定 | 误导用户，且违反不变量 7 | `EpistemicAction` → 语气档位映射 + 渲染后一致性校验 |
| **R5** | **迎合**：为让用户满意而放弃分析 | 系统退化为奉承机器 | 场景 D 专项；元认知的 `user_pleasing_bias_risk` 检查 |
| **R6** | **把用户赞同当事实验证** | 不变量 4 被绕过 | 反馈路径**没有**"置为 VERIFIED"的入口 |
| **R7** | **抽象逃逸**：用抽象语言掩盖事实不足 | 回答看似深刻实则空洞 | 元认知的 `abstraction_escape_risk`；§9.9 明确禁止 |
| **R8** | **虚假平衡**：机械地"双方都有道理" | 失去判断力 | §9.8 明确禁止；`DialecticalAnalysis` 要求给出真实张力 |
| **R9** | **提案门槛被绕过**：单次经验升级为全局策略 | 违反不变量 10 | 门槛以常量实现并测试；`proposal_false_promotion_rate` 硬指标 = 0 |

| **R33** | **预算表与模块矩阵漂移** | 二者住在不同模块，改一处忘一处，"循环永不超预算"在运行期破功 | 三张表（预算 / 标称调用数 / 模块矩阵）的一致性由 `tests/unit/test_orchestrator_and_depth.py` 断言 |
| **R34** | **记忆写入与事件写入不同事务** | 极端情况下可能出现"记忆改了但事件没写" | ✅ **阶段 5 已闭合**：记忆仓储纳入 `UnitOfWork`，四步同事务。由 `TestAtomicity`（注入一个写事件必失败的存储）作为**直接证据**（ADR-0017 §3） |
| **R36** | **推理 token 吃掉输出预算** | 截断 → 分析丢失甚至回合失败 | 推理预留按实测标定（16384）；截断在解析前判定并给出可操作的错误；可选模块降级而非失败。**根治靠提示词约束输出规模，需评测支撑（阶段 7）** |
| **R37** | **真实模型不按 Schema 说话** | 结构化解析失败 | 提取修复（去代码块 / 括号配平扫描）+ JSON 模式 + 有限重试；失败时可选模块降级并留痕。**实测：真实回合中 `logical_analyzer` 的失败几乎全部是截断而非格式** |
| **R38** | **单回合成本远高于直觉** | D4 实测 ~21k 输入 + ~33k 输出（其中推理 ~22k） | 已量化记录（ADR-0016 §10）；预算表限制调用**次数**，但无法限制单次生成长度——这是阶段 7 的评测对象 |
| **R39** | **同一个旋钮有两个默认值** | 改一个毫无效果，排查成本高 | 配置层默认改为 `None`（= 用 Provider 默认值）；`TestReasoningHeadroomPlumbing` 钉死，含 `0` 必须被当作合法配置 |
| **R40** | **V0.1 没有认证层** | `user_id` 由调用方声明，故意传入别人的 id 就能读到别人的记忆 | 作用域过滤防的是"代码写错导致的串号"，**不是恶意调用者**。边界写在 `api/routes/memories.py` 的模块文档里；认证不在 V0.1 范围内，阶段 8 的"已知限制"必须包含它 |
| **R41** | **默认向量是词面的，不是语义的** | 同义改写匹配不上，用户会觉得"系统明明记过却想不起来" | `LocalHashingEmbedding` 的局限写在模块文档与 ADR-0017 §1；换 `openai_compatible` 即得真语义。**风险在于它看起来"能用"**——检索确实工作，只是召回范围比语义窄 |
| **R42** | **冲突阈值随向量空间漂移** | 换语义模型后 0.75 从"很接近"变成"随便两条都算"，线索变成噪音 | 阈值有明确文档标注"针对本地向量标定"，换 Provider 必须重新标定；线索只进审计、不驱动任何有代价的动作，因此漂移的后果是**噪音而非错误判断** |
| **R43** | **换向量 Provider 后旧记忆静默失效** | 检索只比对同版本向量，换 Provider 后**旧记忆一条都检索不到**，且不报任何错 | 这是刻意的（比较两个不同语义空间的向量毫无意义），但必须可修：`MemoryService.reindex` 显式重建；`test_only_matching_versions_are_retrieved` 复现这个状态 |
| **R44** | **向量维度是数据库列的固定属性** | 改了配置却忘了改迁移，写入会被 PostgreSQL 拒绝 | 维度写死在迁移里（用常量而非运行时配置，保证迁移可复现）；`test_stored_vector_has_the_migrated_dimension` 在真实库上核对；`OpenAICompatibleEmbedding` 对返回维度不符**明确失败** |
| **R45** | **反馈正文留在事件流里，不随"删除用户数据"消失** | 用户以为删掉的东西，其**原话**仍躺在只追加的事件表里 | 这是刻意的：反馈正文是对话记录（事件流里本来就存着 `user.message.received` 的正文），摘掉它这条事件就只剩"用户点过一次纠正"。代价是**删除范围与用户直觉不一致**，因此 `DELETE /users/{id}/data` 的响应与文档都写明"只覆盖记忆"（`api/schemas.py`、`api/routes/memories.py`）。是否要提供"擦除反馈正文"的能力，留给用户决定（ADR-0018 §4） |
| **R46** | **归因偏保守，真实错误可能大比例进不了模式发现** | `UNKNOWN_ERROR` 只在用户明确否定时出现，其余判不了的情况**直接不归因**；模式发现因此可能长期沉默 | 这是刻意选的偏向：归错了比不归因更糟（把"当时信息本就不足"判成"推理错误"，系统会学到"这类问题要更保守"，而真正的教训是先取证）。**代价是漏报**。阶段 7 应统计"有多少真实错误根本没进模式发现"，用数据决定要不要放宽判据（ADR-0018 §10） |
| **R47** | **提案的 `possible_regressions` 是模板文字，不是计算结果** | 评审看到一段像分析的文本，误以为系统已经算过影响面 | 字段写的是**通用风险模式**（"针对该情境的改动可能让其他情境变差"），不含任何该提案特有的计算。真正的退化预测需要 Golden Dataset（阶段 7）。模板措辞刻意停在方向上，不给具体改法（ADR-0018 §10） |
| **R48** | **提案的并发防护在内存实现上无法真正验证** | 内存工作单元的方法没有 await 点，两个"并发"流转实际是顺序执行的，测不到交错 | 乐观锁本身由**契约测试**在两个实现上共同验证（`test_stale_version_raises_instead_of_overwriting`，用的是**真实存在过的**旧版本号）；独立评审在真实 PostgreSQL 上复现了真交错：失败方抛 `OptimisticLockError`、终态只有一个、且**没有留下任何事件**（ADR-0019 §4） |
| **R49** | **反馈是 V0.1 里唯一能把任意自由文本写进记忆的生产路径** | 内容层唯一防线是关键词匹配，而 `write_policy.py` 自己声明"关键词匹配必然漏"；反馈硬编码 `sensitivity=PERSONAL`（恰好等于自动写入上限），因此敏感度闸门对它也不生效 | 写入仍必须过 `WritePolicy`（ADR-0004 的白名单、内容红线、确认要求），且记忆标记为 `SELF_REPORTED` 并记录来源反馈事件。**但"用户自己写下并明确要求记下来"这件事本身是正当的**——真正的缺口是内容层没有比关键词更强的判据。列入阶段 7 的评测范围（ADR-0019 §2.8） |
| **R50** | **失败回合不产生经验** | "学习链路只接在 `_close_round`（成功收尾）上"，而失败回合恰恰是最该学的东西 | 失败回合的 `failure_stage` / `error_category` 已经落在回合投影与事件里（不变量 20），信息没丢；缺的是把它转成 `Experience` 的那一步。**这是阶段 7 的显式待办**——归因判据里的 `_from_failure` 分支目前在生产上不可达 |
| **R51** | **学习链路仍有无约束的自由文本通道** | `applicable_conditions` / `counterexamples` / `situation_signature` / `failure_stage` / `fix_direction` 都是自由 `str`；调用方往里填用户原话，它会一路进 `Experience`、`ErrorPattern`、提案的 `applicability` 并持久化 | `RoundRecord` 的字段集合被测试钉死（挡得住"新增一个 `user_message` 字段"），但那**挡不住"往已有字段里填原文"**。残余风险已在两处显式钉成用例（`test_the_field_set_test_is_not_enough_on_its_own` 等）；运行时**不**把 `Judgment.strongest_counterarguments` 填进 `counterexamples`。要变成机制需要长度/格式约束，收益与代价尚未评估（ADR-0019 §3.1） |
| **R35** | **提示词注入** | 用户内容里的三连反引号可以提前闭合数据块，把后续文字变成"指令" | 数据块内容经 JSON 编码后**额外转义反引号**；模板只允许 `{{input}}` 一个占位符；`tests/unit/test_prompt_registry.py` 有用例专门复现这个攻击 |
| **R52** | 🔴 **I01 与 I13 的运行期强制实际为零** | `Hypothesis.is_factual_claim`、`can_be_written_as_fact`、`UserModel.is_confirmable` 都是**常量 `False`**，因此 `assert_hypothesis_not_fact` 与 `assert_user_model_not_confirmed` 的 `raise` 分支**不可达**；这两个守卫在 `src/` 里也**没有任何调用者** | 它们不是防线，是**写在代码里的文档**。真正的保证在类型层（属性没有为 True 的可能）。阶段 6.5 §五.4 要求"每条不变量一个定向反例"，而这两条**造不出反例**——用 monkeypatch 造一个只能证明"monkeypatch 好使"。真实情况被钉在 `tests/unit/test_invariant_counterexamples.py::TestI01AndI13CannotBeBrokenByConstruction` 里：将来属性若被改成真实判断，那条用例会红，改动者必须同时回答"现在的运行期强制是什么" |
| **R53** | **无幂等键的重发会被算作"又发生了一次"** | 客户端不带 `Idempotency-Key` 地重发同一句话，服务端盖一个新的回合，`independence_group` 因此不同，门槛把它算成两次独立发生 | 这是**已知边界**，不是遗漏：要让它塌缩成一次只能靠比较消息正文，而那是**语义判断**，不是本系统做归因的方式（ADR-0020 §2）。带幂等键的重试与事件重放都已被正确处理并有测试 |
| **R54** | **经验的评价只升不降** | `assess_experiences` 取最高一档，而 V0.1 没有"推翻一次确认"的评价路径。一次错误的用户确认会把一条经验**永久**抬到 `CONFIRMED` | 取最高档是刻意的（"最后一条说了算"会让确认被随后的 `SUSPECTED` 无声降级）。降级需要**显式引入一种表达否定评价的评估者**，那时 `assess_experiences` 的合并规则要一并改。在 V0.1 的规模下（经验以百计）影响有限 |
| **R55** | **被裁决过的模式不会再被提议** | 一条提案被驳回后，同一个 `(错误类别, 情境签名)` **永远不会**再生成新提案——即使此后又发生了很多次 | 阶段 6.5 §四 修掉的是反方向（原本会"每跑一次再递一遍"）。这个取舍是显式的：V0.1 没有"重新开启"机制，而"反复递同一份"对评审的伤害更直接。引入重新开启（例如"驳回 N 天后、或新增 M 次发生时可再审"）属于阶段 7，那时改的是 `_covered_keys` 的一行 |
| **R56** | **`evidence` 的长度上限写在 Schema 校验器里而不是 `Field(max_length=...)`** | 同一份 `schemas.py` 里，单值的长度上限用 `Field`、列表项的长度上限用 `field_validator`，两种写法并存 | 原因是 pydantic 的 `max_length` 对 `list` 管的是**条目数**不是**各项长度**，逐项长度只能在校验器里做。风险是改动时容易只改一处。边界行为由 `tests/integration/test_input_contract.py` 在两个后端上钉住 |
| **R57** | **`ProposalGate` 每次复核都要全量读取事件流** | 代价随历史线性增长；经验数量大时一次学习运行会扫很多遍 | V0.1 的经验总量以百计，实测（1713 用例全套跑 113 秒）没有成为瓶颈。阶段 7 若经验量上升到需要分页，读取器需要一个按 `(错误类别, 情境签名)` 的索引——那时改的是 `ExperienceReader`，门禁一行不用动（ADR-0022 影响一节） |
| **R58** | **归因判据里仍有四条在生产上不可达** | `_from_failure`（失败回合不构经验）、`_from_budget`（刻意不喂）、`_from_memory_rejection`（无生产者）、`_from_user_feedback`（反馈在回合之后到达，无回流路径） | 与 R46/R50 同源。阶段 6.5 §二 接通了"反馈抬高评价"这条路径，但**没有**给归因回路加新输入——那需要失败回合产生经验（R50）与记忆拒绝回流，两者都是阶段 7 的显式待办 |

|---|---|---|---|
| C1 | `EntityMetadata` 要求与 13 个类定义不一致 | 全部继承基类 | ✅ ADR-0006 |
| C2 | 阶段 3 场景 F/J 依赖阶段 5 的记忆系统 | 内存适配器 + 契约测试 | ✅ ADR-0009 |
| C12 | `EpistemicAction` 与 `MetacognitiveDecision` 语义重叠 | 拆分为内部控制流 vs 对外建议 | ✅ ADR-0010 |
| C13 | `DEGRADED` 不在回合状态枚举中 | 归入系统健康状态 | ✅ ADR-0012 |

**其余 16 项缺口**（`related_goal_ids` 无 Goal 实体、`Hypothesis.category` 无枚举、
状态超时无数值、元认知调用是否计入预算、`tests/golden/` 与 `evals/datasets/` 职责重叠、
宪法不可测、无用户创建接口等）默认值见 ADR-0008 / ADR-0012。

## 6. 需要持续关注的三个问题

1. **Port 设计**（R12）——✅ 阶段 3 已定型。
   `MemoryRepository` 的形状直接依据任务书 §10 的操作清单，未自创语义。
   阶段 5 的验证点是：换实现时**场景测试一行都不用改**。
2. **契约测试**（R13）——✅ 已建立并立刻证明了自己的价值
   （抓到两处 PostgreSQL 实现的不一致）。
   阶段 5 要做的是把记忆仓储接进 `tests/integration/test_contract_postgres.py`
   里预留的占位类，而不是新写一套。
3. **范围纪律**（R23）——每个阶段结束时仓库必须可运行；
   不可运行就不算完成。
4. **反刍检测的精度**（R32）——当前是词面相似度，只捕捉逐字重复。
   阶段 4 接入真实模型后这个局限已经暴露：真实模型的两次判断会改写措辞，
   因此阈值 0.85 实际上只能捕捉"逐字重复"。
   阶段 5 交付了向量检索的**能力**（`memory/retrieval.py`），但阈值仍是词面标定，
   且默认向量本身就是词面的（R41）——换成外部语义向量之前，
   用它做语义级检测没有意义。**阶段 7 应结合评测数据重新标定阈值**，
   并在此之前决定要不要换向量 Provider。
5. **单回合成本**（R38）——D4 回合实测约 21k 输入 + 33k 输出，其中推理占 22k。
   预算表限制的是**调用次数**，管不住**单次生成的长度**。
   阶段 7 的评测应把"每个任务的合理输出规模"一并标定，
   并把结果反馈到提示词模板里（限定列表长度与条数）。
